# IMX6ULL Linux Learning Roadmap

> 一份可执行的长期学习路线。目标不是"看完多少教程"，而是每完成一个阶段，都能在真实的 i.MX6ULL 板子上跑出东西，并在本仓库留下可复查的成果。

最后更新：2026-09-18

---

## 一、目标与起点

### 最终目标

1. 系统学习嵌入式 Linux，补齐从 MCU 转向 Linux 之后的知识体系
2. 通过实际实验掌握 Linux C、进程线程、网络、驱动、设备树，而不是只看教程
3. 完成一个完整项目：Ubuntu 上的 OCPP 云平台/模拟服务端 + i.MX6ULL 模拟充电桩，并逐步加入充电状态机、网络通信、故障处理、数据持久化
4. 仓库作为长期学习记录与项目作品，commit 历史、实验记录、问题排查记录都要有实际价值
5. 大量使用 Codex 辅助学习，但不变成"AI 写完了、我完全不会"的代码搬运

### 已有基础

- MCU 开发经验：寄存器级编程、外设驱动、中断、定时器
- C 语言熟练，熟悉 CAN 总线
- 有充电桩业务开发经验（这是最终项目的领域优势）
- 已完成交叉编译工具链的安装，Stage 0 继续验证实际交叉编译与板端运行

### 薄弱环节

- Linux 用户空间开发经验少：文件 IO、进程、线程、IPC、网络编程
- 没有内核侧开发经验：内核模块、字符设备、设备树
- Linux 命令行与系统模型还在建立阶段

### 要解决的核心问题

从**裸机思维/RTOS**切换到 **Linux 系统思维**。这是整条路线最关键、也最容易卡住的一步。

| 裸机 / MCU/ RTOS | Linux |
| --- | --- |
| 一个程序占用整个 CPU | 多个进程由内核调度，彼此隔离 |
| 直接读写物理地址 | 只能通过虚拟地址，用户空间不能直接碰硬件 |
| 中断服务程序直接处理一切 | 内核上半部 / 下半部，用户空间通过系统调用间接访问 |
| 外设 = 一组寄存器 | 外设 = 设备树节点 + 驱动 + `/dev` 或 `/sys` 接口 |
| "我控制一切" | "我申请资源，内核决定是否给我" |
| 代码写错最多是不工作 | 内核代码写错会导致系统崩溃或数据损坏 |

有 MCU 背景是优势：时序、寄存器、中断、总线这些概念你已经具备，缺的只是"操作系统这一层如何插在你和硬件之间"。

### 这条路线怎么用

1. 按阶段顺序推进。前一阶段的能力是后一阶段的前提。
2. 每阶段都有**核心必做**和**可选强化**。核心必做达成即可进入下一阶段，不要为了打勾清单而做完全部实验。
3. 参考周期只是估算。**"阶段目标达成"比"按时间完成"重要。**
4. 每阶段结束用"阶段结束时应达到"自检。答不上来就回去补，不要硬推进。
5. 掌握程度分三档，见第五章：**必须掌握**（能独立写、能讲清原理）、**理解即可**（知道是什么、用时能查）、**暂时不用学**（避免分散精力）。

## 二、开发环境

| 环节 | 选型 |
| --- | --- |
| 主机 | Windows + VS Code |
| 连接方式 | VS Code Remote - SSH → VMware Ubuntu 虚拟机（IP 以当前网络环境为准） |
| 开发机 | Ubuntu 24.04 |
| 交叉工具链 | `gcc-linaro-4.9.4-2017.01-x86_64_arm-linux-gnueabihf`（已安装） |
| 目标板 | i.MX6ULL |
| 仓库 | 开发机本地工作副本，远程托管在 GitHub |

具体的主机名、IP、端口只保存在本机的 `~/.ssh/config` 里，**不提交到仓库**——内网地址会随环境变化，写进公开仓库既会失效也会暴露内网信息。

### 三条铁律

1. **所有代码、构建、Git 操作都在 Ubuntu 上完成**。Windows 只作为编辑器和终端前端，不保留第二份代码副本。
2. **内核、U-Boot、工具链、rootfs、镜像一律放在仓库之外**。仓库只记录它们的版本与获取方式，不存放本体。
3. **每个实验结束就提交一次**，不要攒到最后。commit 历史本身就是学习记录。

### 关于版本的重要提醒

本路线**不假设任何具体的 Kernel / U-Boot 版本**。

- 已安装的 Linaro 4.9.4 工具链属于较早期版本，但**它对应的具体 BSP 内核版本尚未验证**，不能当作已知事实。
- 驱动、设备树、GPIO、中断、总线这些内容属于长期知识体系，但**具体 API 与写法必须以下一步确认的实际版本为准**。
- 原因：Linux 4.1.x / 4.9 / 5.4 / 6.x 之间，`file_operations` 的成员、GPIO 子系统（新旧两套 API）、`copy_to_user` 的返回值约定、设备树 binding、pinctrl 写法都有实际差异。网上大量示例是按较新内核写的，直接照抄会编译不过或行为异常。
- 因此 **Stage 0 的第一件事就是确认并记录真实版本信息**，后续所有阶段都以它为基准。

## 四、阶段详情

### Stage 0：环境确认与最小闭环（1 周）

**学习目标**

建立"写代码 → 交叉编译 → 放到板子 → 运行 → 看结果"的最小闭环，并确认开发环境的真实版本信息。

**为什么学**

后面每个阶段都要反复走这条回路。它不通，后面每一步都会变成折磨。而版本信息是所有后续内容的前提——驱动 API 和设备树写法完全取决于它。

**核心必做**

- 确认并记录：BSP 来源、**Kernel 版本**、**U-Boot 版本**、设备树文件位置、**交叉工具链版本**
- 串口连接板子，确认能正常启动到 shell，并保存完整启动日志
- 验证交叉编译工具链可用
- 交叉编译一个最小的 ARM 程序
- 部署到板子并成功运行
- SSH / SCP 等基础操作（板子支持网络的话）

**推荐实验**

- 【必做】写 `hello.c`，交叉编译后用 `file` 确认产物是 ARM ELF，传到板子运行
- 【必做】把板子上电启动的完整串口日志保存到 `docs/00-env/`，作为后续排查问题的基线
- 【必做】写一个 `build.sh` 或 Makefile，一条命令完成"编译 + 传输 + 加执行权限"
- 【选做】先在开发机上用 `qemu-arm` 运行同一个二进制，体会"架构不同不能直接跑"

**可选强化**

- TFTP 加载内核 + NFS 挂载根文件系统
- 板子静态 IP 配置、TFTP/NFS 服务端配置

> TFTP/NFS 很重要，但**不必在 Stage 0 卡住**。建议在进入 Stage 5（驱动）之前完成即可——因为驱动调试需要频繁重载模块，用烧卡方式做会非常痛苦。

**阶段结束时应达到**

不看教程也能独立完成"写 → 编译 → 部署 → 运行"闭环；能准确说出自己板子的 Kernel / U-Boot / 工具链版本。

**与 OCPP 项目的关系**

这个闭环就是以后 OCPP 客户端在板子上部署和更新的方式。脚本化之后，每次改代码到板子上验证只需要一条命令。

**Codex 如何辅助**

帮你解读串口启动日志里的关键信息（内核版本、设备树加载、启动参数）；帮你理解 `file` / `readelf` 的输出含义。这一阶段的环境类报错可以直接问，没必要自己死磕。

**GitHub 应留下的学习记录**

- `labs/00-toolchain/`：hello 程序 + 构建脚本 + README
- `docs/00-env/`：**版本信息表** + 串口启动日志基线 + 部署流程说明

### Stage 1：Linux 基础与命令行（2~3 周）

**学习目标**

能用命令行自如地操作 Linux，理解进程、权限、文件系统的运作方式。

**为什么学**

命令行是 Linux 的母语，也是板子上通常唯一的交互方式。后面调试驱动时，大量时间花在 `/proc`、`/sys`、`dmesg` 之间。

**核心必做**

- 目录结构与 FHS：`/etc` `/var` `/proc` `/sys` `/dev` 各自的角色
- 权限模型：用户 / 组 / `rwx` / `chmod` / `chown`、特殊权限位
- 进程与作业控制：`ps` / `top` / `kill` / 前后台 / `nohup`、进程状态
- 管道与重定向：`|` `>` `>>` `<` `2>` `tee`
- 文本处理：`grep` / `sed` / `awk` 基本用法，`find` / `xargs`
- 包管理与 systemd 服务（unit、开机自启、`journalctl`）
- 网络基础命令：`ip` / `ping` / `ss` / `scp` / `ssh`
- `/proc` 与 `/sys` 的区别与用途

**推荐实验**

- 【必做】写一个板子状态巡检脚本：CPU 温度、内存、磁盘、网络、关键进程
- 【必做】"解剖"一个进程：用 `ps` 加 `/proc/<pid>/*` 观察它的内存映射、打开的文件、环境变量
- 【必做】把自己写的一个程序做成 systemd 服务并开机自启，用 `journalctl` 查看日志
- 【选做】在板子上实现同样的自启（板子通常是 busybox init 或 SysV 脚本，与 systemd 的差异值得记录）
- 【选做】用 `grep` / `sed` / `awk` 对 `dmesg` 输出做统计

**可选强化**

- Shell 脚本的函数、数组、错误处理（`set -e`、`trap`）
- systemd 的依赖关系与 target
- 磁盘与文件系统管理（分区、挂载、`fstab`）

**阶段结束时应达到**

不用图形界面，仅靠命令行完成查找、过滤、批处理；能读懂一个进程的状态；能说清 `/proc` 与 `/sys` 的区别。

**与 OCPP 项目的关系**

充电桩部署在板子上通常没有图形界面，运维、排障、日志分析全靠命令行。你写的巡检脚本稍加改造就能变成项目的诊断脚本。

**Codex 如何辅助**

帮你把零散命令整理成可复用脚本；解释 `sed` / `awk` 表达式；帮你读懂 `/proc` 里各项的含义。这一阶段可以让 Codex 多写脚本，但常用命令要自己动手敲熟。

**GitHub 应留下的学习记录**

- `labs/01-linux-basics/`：脚本，每个配 README 说明用途与用法
- `docs/01-linux-basics/`：命令速查表 + 踩坑记录

### Stage 2：Linux C 应用与文件 IO（2~3 周）

**学习目标**

能读懂并写出规范的用户空间 C 程序，理解"程序如何通过系统调用与内核交互"。

**为什么学**

这是用户空间开发的地基。之后的驱动测试程序、网络程序、OCPP 客户端，写法都建立在这一层之上。

**核心必做**

- gcc 编译流程：预处理 → 编译 → 汇编 → 链接，以及各阶段产物
- 系统调用与标准库的差异（`open` vs `fopen`，缓冲发生在哪一层）
- 文件描述符的本质
- `open` / `read` / `write` / `lseek` / `close` / `ioctl` / `stat`
- `errno` 与错误处理规范
- Makefile：变量、模式规则、伪目标、依赖关系
- 静态库与动态库的制作与链接

**推荐实验**

- 【必做】实现自己的 `cp`，完整处理错误路径（源文件不存在、目标不可写、空间不足）
- 【必做】用 `ioctl` 操作板子上现成的设备节点（例如板载 LED），观察用户空间到驱动的完整调用链
- 【必做】把多文件项目用 Makefile 组织起来，产出静态库与动态库各一个并分别链接
- 【选做】实现简化版 `cat`，支持多文件与标准输入
- 【选做】用 `strace` 对比自己的程序与系统命令的系统调用差异

**可选强化**

- 缓冲 IO 与直接 IO 的行为差异
- `mmap` 文件映射
- 动态库的运行时查找路径（`LD_LIBRARY_PATH`、`ldconfig`）

**阶段结束时应达到**

看到一段 C 代码，能说出它大致会触发哪些系统调用；能写出带完整错误处理的文件操作代码；能读懂并修改别人的 Makefile。

**与 OCPP 项目的关系**

OCPP 客户端的配置读写、日志落盘、交易记录持久化，以及后续对串口 / CAN 设备的读写，全部是这一层的直接应用。文件 IO 写得不严谨，项目上线后就是丢配置和丢交易记录。

**Codex 如何辅助**

Makefile 与工程骨架可以直接让它生成，不必手写；让它 review 你的错误处理是否覆盖了所有失败路径——这是新手最容易漏的地方；用 `strace` 输出帮你理解"程序实际做了什么"。

**GitHub 应留下的学习记录**

- `labs/02-linux-c-io/`：每个工具独立目录，含源码、Makefile、README
- `docs/02-linux-c/`：笔记，重点记录标准库与系统调用的差异这类易混点

### Stage 3：进程、线程与 IPC（3~4 周）

**学习目标**

理解 Linux 的并发模型，能写出正确、健壮的多进程 / 多线程程序。

**为什么学**

充电桩是天然并发的系统：它同时要与云平台通信、采集数据、控制硬件、跑状态机、写日志。**并发写错会出现"偶尔才复现"的 bug**，这类问题在嵌入式现场极难定位。

**核心必做**

- `fork` / `exec` / `wait` / `waitpid` 的语义与组合用法
- 进程状态、僵尸进程与孤儿进程的成因
- 信号：注册处理函数、`SIGCHLD` / `SIGTERM` / `SIGINT`、信号处理的限制
- pthread：创建、`join`、分离
- 同步原语：互斥锁、条件变量
- 竞态与死锁的成因与识别方法
- 至少掌握一种 IPC：管道（匿名 / FIFO）、共享内存、消息队列或信号量

**推荐实验**

- 【必做】生产者-消费者：多线程 + 互斥锁 + 条件变量实现有界队列
- 【必做】故意制造一次竞态（两个线程同时对同一变量做 `++`），观察错误结果，再用锁修正
- 【必做】写一个多线程日志模块：并发写同一文件不冲突，支持日志级别
- 【选做】简化版 shell：`fork` + `exec` + `wait` 执行命令，支持管道连接两个命令
- 【选做】用共享内存 + 信号量在两个进程间传数据，并与管道方案对比
- 【选做】故意制造一次死锁，用 gdb 定位，把完整排查过程写进笔记

**可选强化**

- 守护进程编写要点（double fork、`setsid`、重定向标准流）
- 简单线程池的实现
- 各类 IPC 的适用场景对比

**阶段结束时应达到**

能判断一段并发代码可能在哪儿出问题；能用正确的同步原语解决；能解释 `fork` 之后父子进程的内存与文件描述符关系。

**与 OCPP 项目的关系**

这是项目里复用最直接的能力。OCPP 客户端至少要拆成通信线程、业务 / 状态机线程、采集线程、日志线程，它们之间需要队列与同步。Stage 3 写的有界队列和日志模块可以直接演进成项目组件。

**Codex 如何辅助**

并发问题最难的是"看不见"，可以让它帮你分析死锁 / 竞态的**排查思路**（而不是直接给答案），帮你设计压测场景。但 `fork` / pthread 的代码必须自己写——这是本阶段必须掌握的核心。

**GitHub 应留下的学习记录**

- `labs/03-process-thread-ipc/`：完整可编译的示例程序
- `docs/03-concurrency/`：**"竞态复现与死锁定位"这类过程记录是极佳的面试素材**

### Stage 4：网络编程（3~4 周）

**学习目标**

能写出稳定的 TCP 服务端 / 客户端，理解应用层协议的设计与实现。

**为什么学**

OCPP 的传输层就是 WebSocket over TCP/TLS。这一阶段是充电桩项目最直接的前置。你有 CAN 经验，会发现应用层协议设计与 CAN 分帧思路相通。

**核心必做**

- TCP/IP 分层模型与每层在代码中的对应
- socket 完整生命周期：`socket` / `bind` / `listen` / `accept` / `connect` / `send` / `recv`
- 字节序与地址转换（`htonl`、`inet_pton` 等）
- TCP 与 UDP 的取舍
- 阻塞 / 非阻塞 / IO 多路复用：`select` / `poll` / `epoll`（**以 `epoll` 为重点**）
- **粘包与拆包**的成因与解决
- 应用层协议设计：长度前缀、消息边界、协议状态机
- HTTP 报文格式基础
- WebSocket **基本原理**：握手过程、帧结构

**推荐实验**

- 【必做】TCP echo 服务端 + 客户端
- 【必做】用 `epoll` 改写服务端，支持多客户端并发，并正确处理客户端异常断开
- 【必做】自己设计一个带长度前缀的应用层协议，实现可靠收发并处理粘包（可以对照 CAN 的 `ID + DLC + Data` 结构设计）
- 【选做】实现最小 HTTP 服务器，用浏览器访问
- 【选做】用 C 完成一次 WebSocket 握手并收发一帧文本消息——**目的是理解帧结构，不是造协议栈**
- 【选做】让板子作为客户端连接开发机上的服务端，在真实硬件上跑一遍

**可选强化**

- TLS 与 OpenSSL 库的基本调用（会调用即可，不必理解握手细节）
- 多路复用中的定时器与超时管理
- 服务端并发压测

**阶段结束时应达到**

能独立写出稳定的 TCP 服务端；能解释粘包为什么发生、怎么解决；能读懂 WebSocket 帧结构。

**与 OCPP 项目的关系**

这就是云桩通信的底座。`epoll` 服务端骨架、长度前缀协议的思维、断线检测与重连逻辑，都会直接进入 OCPP 客户端。**WebSocket 层在项目中使用成熟库，不需要自己实现**——你的目标是理解它，而不是重复造轮子。

**Codex 如何辅助**

帮你 review 网络代码的错误处理（连接被对端关闭、部分发送、`EAGAIN` 处理是最容易漏的）；帮你设计粘包与异常场景的测试用例。TCP / `epoll` 的核心代码自己写，让 Codex 检查。

### Stage 5：字符设备驱动（3~4 周）

**学习目标**

理解 Linux 驱动的运行模型，能写出一个规范的字符设备驱动。

**为什么学**

这是"会写应用"到"理解系统"的分水岭，也是后面 GPIO、中断、总线驱动的基础。

> **版本提醒**：本阶段所有 API 与写法，**必须以 Stage 0 确认的实际 Kernel / BSP 版本为准**。不同内核版本在 `file_operations` 成员、字符设备注册方式、`copy_to_user` 返回值约定上都有差异，网上示例常与你的 BSP 不匹配。

**核心必做**

- 内核模块的编译、加载、卸载（`insmod` / `rmmod` / `lsmod` / `modinfo`）
- `printk` 与日志级别、`dmesg` 的使用
- 字符设备的注册方式（按你的内核版本选择合适做法）
- `file_operations` 结构体与每个回调的调用时机
- `copy_to_user` / `copy_from_user`，以及用户 / 内核空间隔离的根本原因
- `ioctl` 命令编码（`_IO` / `_IOR` / `_IOW` / `_IOWR`）
- 内核并发控制：自旋锁与互斥锁的区别与选用
- 内核错误返回值规范（`-EINVAL` / `-EFAULT` / `-ENOMEM` 等）

**推荐实验**

- 【必做】第一个内核模块：加载 / 卸载时打印，用 `dmesg` 观察
- 【必做】最简字符设备：支持 `open` / `read` / `write` / `release`，用 `cat` 和 `echo` 验证
- 【必做】加上 `ioctl`，并写一个独立的用户态测试程序
- 【选做】用多线程压测你的设备，先观察不加锁的问题，再加锁解决
- 【选做】补全所有错误路径的返回值

**可选强化**

- 内核内存分配（`kmalloc` 与 `vmalloc` 的差别）
- 阻塞与非阻塞 IO 在驱动侧的实现
- 内核定时器

**阶段结束时应达到**

能独立写出规范可用的字符设备驱动；能说清为什么用户空间 buffer 不能直接解引用；能解释 `file_operations` 中每个函数在什么时候被调用。

**与 OCPP 项目的关系**

字符设备模型是充电桩与硬件交互的抽象基础。后面使用标准子系统（`gpio-keys`、SocketCAN）控制硬件时，看到的 `/dev` 节点正是这个模型；理解它，也是你能排查"设备打不开 / 读不到数据"这类问题的前提。

**Codex 如何辅助**

内核报错信息往往很晦涩，定位这类问题可以直接问，效率最高；让它审查你的错误路径与并发保护是否完整。模块骨架可以生成，但 `file_operations` 里每个函数的实现必须自己写。

**GitHub 应留下的学习记录**

- `labs/05-chardev/`：驱动源码 + 用户态测试程序 + Makefile + README（写清如何加载、如何创建设备节点、现象是什么）
- `docs/05-driver-basics/`：驱动的加载 / 卸载流程与常见错误

### Stage 6：设备树、GPIO 与中断（3~4 周）

**学习目标**

能看懂并修改板子的设备树，把外设接到自己的驱动上，能写带中断的驱动。

**为什么学**

i.MX6ULL 上几乎所有外设都是"设备树描述 + 驱动解析"。不会设备树，换个引脚就不会用，也看不懂 BSP 与原理图的对应关系。

> **版本提醒**：dts 语法本身相对稳定，但 binding 写法、pinctrl 配置和 GPIO API（`gpiod_*` 与旧版接口）都随内核版本变化。**以你板子实际的设备树与内核版本为准**，不要照抄其他版本的示例。

**本阶段核心：设备树 + GPIO 子系统 + 驱动。** 用户态访问 GPIO 的几种方式只作为背景了解，不需要三套都深入学习。

**核心必做**

- 设备树的作用；`dtc` 编译与反编译
- 语法：节点、属性、引用、`compatible`、`status`
- `compatible` 与驱动的匹配机制（`of_match_table`）
- pinctrl 引脚复用，以及为什么必须与 GPIO 声明配对
- GPIO 子系统与 `gpiod` 相关 API
- 中断：`request_irq`、中断上下文的限制、上半部与下半部
- 用户态访问 GPIO 的几种方式（sysfs / 字符设备 / 库）——**了解即可**：知道存在这些途径与各自适用场景就行，不必三套都深入

**推荐实验**

- 【必做】先用 `gpio-leds` / `gpio-keys` 标准 binding，通过修改设备树点亮自己的 LED、读出按键——先不写驱动，体会设备树的作用
- 【必做】写一个 `platform_driver`，通过 `compatible` 与自己的设备树节点匹配成功
- 【必做】按键中断驱动 + 去抖处理
- 【选做】给中断驱动加阻塞读或 `poll`，让用户空间能实时收到按键事件
- 【选做】用 `gpioinfo` / `gpiodetect` / debugfs 验证 GPIO 的实际状态

**可选强化**

- 设备树 overlay
- 工作队列与 tasklet 的选择
- 中断线程化（threaded IRQ）

**阶段结束时应达到**

能看懂板子设备树并把外设接到自己的代码上；能写一个带中断的完整驱动；能解释 pinctrl 配错会导致什么后果。

**与 OCPP 项目的关系**

**这是充电桩硬件模拟的核心。** 充电枪插拔检测（GPIO 输入 + 中断）、继电器控制（GPIO 输出）、充电指示灯、按键，全都依赖这一阶段的能力。你在裸机时代靠直接写寄存器控制这些，现在要习惯"设备树描述 + 子系统"的方式。

**Codex 如何辅助**

帮你解读板子现有 dts 中某个节点的含义；帮你分析"驱动没有被 probe"这类问题的排查路径；帮你检查中断处理函数有没有违反"中断上下文不能睡眠"这类规则。

**GitHub 应留下的学习记录**

- `labs/06-dts-gpio/`：驱动 + 设备树片段 + 用户态测试程序
- `docs/06-dts-gpio/`：设备树语法速查 + **自己板子的 GPIO 引脚分配表**（后续会反复用到）

### Stage 7：总线与外设（重点 CAN）（2~3 周）

**学习目标**

能用 Linux 的方式访问板级总线设备，重点是 CAN。

**为什么学**

充电桩原型必然要对接外部设备：电表（常见 RS485/Modbus，本质是串口）、温度传感器（I2C）、BMS 通信（CAN）。你已有的 CAN 经验在这里能直接复用到 Linux 侧。

**核心必做**

- SocketCAN 模型：`can0` 接口、`candump` / `cansend`
- 用 C 通过 socket 收发 CAN 报文
- CAN 过滤器与错误帧的基本处理
- I2C：设备树节点写法、`i2c-tools` 用户态访问
- 串口基础（后续对接 Modbus 电表会用到）

**推荐实验**

- 【必做】CAN 回环或双节点实验：配置 CAN 接口，用 `candump` / `cansend` 收发
- 【必做】用 C 实现 CAN 报文收发，并把 CAN 数据映射成应用层数据结构（为模拟 BMS 做准备）
- 【必做】用 `i2cdetect` 扫描总线，确认板子上实际的 I2C 设备
- 【选做】在设备树里添加 I2C 传感器节点并读通数据
- 【选做】串口收发实验（对接 Modbus 电表的前置）

**可选强化**

- SPI 基础
- regmap（理解即可）
- 写一个 I2C 设备的内核驱动

**阶段结束时应达到**

能在 Linux 下用 C 程序稳定收发 CAN 报文；能独立给板子添加一个 I2C 设备并读通数据；能判断哪些外设用用户态访问就够、哪些必须写内核驱动。

**与 OCPP 项目的关系**

CAN 是充电桩与 BMS 通信的标准方式，也是你原有 CAN 经验与 Linux 的衔接点。I2C 与串口用于传感器和电表。这一阶段做出的 CAN 收发模块，之后可以直接演变成项目里的"模拟 BMS"。

**Codex 如何辅助**

帮你理解 SocketCAN 与裸机 CAN 控制器编程的差异（这是你最可能困惑的地方）；帮你设计 CAN 报文到应用数据的映射；生成 I2C / 串口实验的脚手架。

**GitHub 应留下的学习记录**

- `labs/07-bus/`：CAN 工具与 I2C 实验
- `docs/07-bus/`：CAN 报文与应用数据的映射设计

### Stage 8：OCPP 云平台 + i.MX6ULL 模拟充电桩（8~12 周）

**学习目标**

完成一个可演示的完整系统：Ubuntu 上的 OCPP 服务端 + i.MX6ULL 上的模拟充电桩。

**为什么学**

这是把所有阶段串起来的项目，也是简历上最有分量的内容。

> **实施顺序：先跑通 Ubuntu CSMS ↔ OCPP ↔ i.MX6ULL ↔ 充电桩状态机这条主线，再逐步加入 GPIO、CAN、持久化与异常场景等增强功能。**

**核心必做**

- OCPP 协议理解：`CALL` / `CALLRESULT` / `CALLERROR` 三种报文
- 核心消息：`BootNotification`、`Heartbeat`、`StatusNotification`、`Authorize`、`StartTransaction`、`MeterValues`、`StopTransaction`
- WebSocket 承载与消息 ID 机制（**使用成熟库，不自己实现协议栈**）
- Ubuntu 上搭建服务端：自建最简 CSMS，或使用开源实现
- 充电桩状态机：空闲 / 已连接 / 充电中 / 已充满 / 故障
- 事务管理：启动、计量上报、正常停止、异常终止
- 断线重连与心跳超时处理
- 数据持久化：交易记录、配置、未上报数据
- 离线缓存与补传
- 交叉编译并部署到 i.MX6ULL，长时间运行验证

**推荐实验 / 交付（按顺序推进）**

- 【第一步·主线】纯软件原型：在开发机上把客户端与服务端的完整充电流程跑通。**把协议逻辑和硬件问题分开调试**，否则出错时无法判断是哪一层的问题
- 【第二步·主线】移植到 i.MX6ULL：交叉编译并部署，打通 Ubuntu CSMS ↔ OCPP ↔ i.MX6ULL ↔ 充电桩状态机 的完整链路
- 【第三步·增强】GPIO 接入：继电器控制充电开关、LED 模拟充电指示灯、按键模拟插枪
- 【第四步·增强，主线跑通之后】CAN 接入：模拟 BMS 上报电压 / 电流 / SOC
- 【第五步·增强】数据持久化与离线缓存补传
- 【第六步·增强】异常场景验证：断网、服务端重启、板子掉电重启后的状态恢复
- 【选做】简单可视化页面，展示充电状态与实时数据
- 【选做】初步支持 OCPP 2.0.1

**可选强化**

- TLS 加密连接
- 多充电枪 / 多连接支持
- 远程固件升级相关消息
- 压力测试与长稳测试

**阶段结束时应达到**

能独立设计并实现一个嵌入式网络客户端项目；能解释项目中每一处技术选型的理由和代价。

**与 OCPP 项目的关系**

这个阶段本身就是项目。

**Codex 如何辅助**

帮你梳理协议交互时序；帮你 review 状态机设计（状态是否完备、异常分支是否覆盖）；帮你设计异常测试用例；帮你分析长稳运行中的资源泄漏。**核心逻辑——状态机、消息处理、持久化——必须自己写。**

## 七、Codex 协作工作流

### 核心原则

**Codex 用来加速理解，不是用来替代理解。**

判断标准很简单：**三个月后，你能不能不看代码就把它讲清楚？** 如果不能，这段代码就不属于你。

### 三类内容，三种处理方式

| 内容类型 | 举例 | 处理方式 |
| --- | --- | --- |
| 重复性 / 模板性 | Makefile、构建与部署脚本、日志框架、目录骨架、正则表达式 | **直接让 Codex 生成**，快速通过，不必手写 |
| 需要理解其逻辑的工程代码 | 配置解析、错误处理、数据转换、测试脚本 | Codex 生成后，**关键逻辑必须能讲清楚**，不懂的地方追问到懂 |
| 核心逻辑 | fork / exec、pthread 同步、socket / epoll、`file_operations`、设备树节点、状态机、OCPP 消息处理 | **自己先写**，Codex 只做引导与检查 |

判断一段代码属于哪一类，问自己："面试时被追问这一处，我能不能讲出来？"

### 标准协作流程（8 步）

1. **我先尝试**——写下自己的理解或简陋实现，哪怕是错的
2. **Codex 先提示，不给完整答案**——明确要求它"只指出方向"
3. **我解释自己的理解**——用自己的话复述原理和思路
4. **Codex 检查我的理解**——指出偏差和遗漏
5. **再给代码片段或修改建议**
6. **我运行实验，观察结果**
7. **记录结果**——现象、结论、踩坑
8. **形成实验 README 或学习笔记并提交**

这套流程适用于学习新概念和写核心代码。**已经掌握、只是重复性的内容，直接跳到第 5 步即可**，不必每次都走完整流程。

### 可以随时直接找 Codex 的场景（不必走完整流程）

- 环境、工具链、编译报错的定位
- 概念解释（可以要求它用 MCU / CAN 的类比来讲）
- 生成实验框架、Makefile、测试脚手架
- 分析报错信息
- 代码 review
- 帮你设计测试用例与边界条件

### "不能只复制运行"的核心清单

以下内容，必须能自己讲清楚——不是要求全部手打，而是**必须理解**：

`fork` / `exec`、pthread 同步、socket、`epoll`、`file_operations`、设备树节点、状态机、OCPP 消息处理

对每一处，至少要能回答：

- 为什么这样写？换个写法会怎样？
- 错误路径（失败、超时、资源不足）怎么处理？
- 删掉其中某一行会发生什么？

### 避免变成代码搬运工的机制

1. **核心逻辑先写后问**。跳过这一步，学习就失效了。
2. **遇到 bug 先要求引导**。明确说"先别给答案，告诉我该往哪个方向排查"，自己定位后再让 Codex 确认思路。
3. **三问检验**。上面那三个问题答不上来，就自己重写一遍。
4. **追问代价**。Codex 给方案时问"为什么选它、有什么代价"。不理解为什么这么选，就不要用。
5. **定期"断网"练习**。每个阶段挑一个实验，完全不问 Codex 独立完成。这是检验真实水平的唯一方法。
6. **每周至少一次口述**。把这一周学到的东西讲一遍（讲给自己、或写进笔记），讲不下去的地方就是没真正学会的地方。

### 建议的提问格式

给足上下文，Codex 才能给出有用的回答：

```
当前阶段：Stage 5（字符设备驱动）
环境：i.MX6ULL，Kernel/U-Boot 版本 <填写实际版本>，工具链 <填写实际版本>
目标：实现一个支持 ioctl 的字符设备
我已经做了：<描述进度和已写的代码>
现象/报错：<完整粘贴报错原文，不要只说"报错了">
我已经尝试过：<说明排查过程>
我希望你：只指出方向，不要直接给完整代码
```

最后一行很关键——它会显著改变回答方式，从"替你写"变成"教你写"。

## 八、学习记录与 Git 约定

- **一个实验一个 commit**，不要攒到最后。
- commit message 写清"做了什么 + 学到了什么"，而不只是"完成"。
  - 好例子：`lab: 字符设备支持 ioctl 读写配置，理解 _IOW 命令编码`
  - 差例子：`update`、`修改`、`111`
- **把失败的尝试写进笔记提交**。面试时"我怎么定位这个 bug"比"我写了这个驱动"更有说服力。建议把失败过程写进 `docs/` 的笔记，而不是提交坏代码。
- 每个阶段结束做一次 `docs:` 提交，写阶段小结与自检结果。
- 未来的你和面试官都会看 commit history。**不要提交自己不理解的 AI 生成代码。**

### 每周节奏建议（按 8~10 小时估算）

- 40% 动手实验
- 30% 理论学习（书、官方文档、视频）
- 20% 写笔记与整理提交
- 10% 复盘上一阶段的薄弱点

## 九、常见陷阱

1. **不清楚自己的内核版本就开始写驱动**。不同版本的 API 有实际差异，先确认再动手。
2. **在 Stage 0 卡太久**。最小闭环通了就往前走，TFTP/NFS 可以等驱动阶段前再补。
3. **一上来就啃内核源码**。内核源码是工具书不是教材，按需查函数实现即可。
4. **只跟着视频敲代码**。视频看完就忘，实验做完才记得住。
5. **试图把每个阶段的实验都做完**。核心必做达成即可推进，可选强化留给有余力的时候。
6. **不写笔记**。三个月后你会忘记当时为什么这么写，笔记是唯一能还原现场的东西。
7. **让 AI 写完就提交**。短期看进度很快，长期看等于没学。
