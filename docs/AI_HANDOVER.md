## 1. 项目背景与目标

### 1.1 为什么学习 i.MX6ULL

学习者的本职方向是充电桩/嵌入式业务开发，已有 MCU、C 语言、CAN 总线和充电桩协议的工程经验，但**没有 Linux 侧（用户空间 + 内核）的开发经验**。选择 i.MX6ULL 是因为它属于典型的 ARM Cortex-A7 + 完整 BSP 的工业级平台，资料生态成熟，且在充电桩行业中被广泛使用，学习成果可以直接迁移到本职工作中。

### 1.2 最终希望掌握的嵌入式 Linux 能力

1. Linux 基础与命令行（命令行是板子上唯一的交互方式）
2. Linux C 应用开发与文件 IO
3. 进程、线程、IPC
4. 网络编程（socket / epoll / 应用层协议）
5. 字符设备驱动开发
6. 设备树、GPIO、中断
7. 板级总线（重点 CAN，其次 I2C/串口）
8. 完成 **OCPP 云平台 + i.MX6ULL 模拟充电桩** 综合项目

### 1.3 目前采用的学习方式

- **路线驱动**：严格按 `docs/roadmap.md` 的 Stage 0 → Stage 8 顺序推进，不跳阶段。
- **实验优先**：每个阶段的核心必做都必须动手跑出结果，不看纯理论。
- **成果入库**：每个实验在仓库留下源码 + Makefile + README（模板见 roadmap 第六章）。
- **区分优先级**：每个阶段都有「核心必做」与「可选强化」，核心必做达成即可进入下一阶段，不追求把清单全部打勾。
- **仓库定位**：GitHub 仓库是长期学习记录与求职作品集，commit 历史必须能真实反映学习过程。

### 1.4 AI 与学习者各自承担什么

这是本项目**最需要被接手 AI 尊重**的一条约定，详见 `docs/roadmap.md` 第七章。

| 角色 | 承担的工作 |
| --- | --- |
| **学习者** | 核心逻辑自己写：`fork`/`exec`、pthread 同步、socket/`epoll`、`file_operations`、设备树节点、状态机、OCPP 消息处理 |
| **AI** | 解释概念、给出排查方向（不直接给答案）、review 代码、分析报错、生成模板与重复性代码（Makefile、构建脚本、正则、目录骨架）、设计测试用例 |

### Stage 0：环境确认与最小闭环

**学习目标**
确认板子的真实版本信息，并打通"写代码 → 交叉编译 → 部署到板子 → 运行 → 看结果"的最小闭环。

**前置知识**
无。这是起点。

**需要学习者亲自动手完成的练习**

1. 查清开发板厂商、型号，找到 BSP 资料并放到 Ubuntu 上（**这一步必须学习者自己做，AI 无法代劳**）
2. 从串口启动日志或 BSP 资料中读出 **Kernel 版本、U-Boot 版本、设备树文件名、工具链版本**，填写到 `docs/00-env/versions.md`
3. 把 USB 转串口透传进虚拟机（VMware 的"可移动设备"菜单），确认出现 `/dev/ttyUSB0`
4. 完整捕获一次开机启动日志，保存为 `docs/00-env/boot-log-baseline.txt`
5. 写一个 `build.sh` 或 Makefile，一条命令完成"交叉编译 + scp 到板子 + 加可执行权限"，放进 `labs/00-toolchain/`
6. 交叉编译一个 `hello.c`，部署到板子运行，看到输出
7. 用 `file` 对比 ARM 与 x86 产物的差异，把结论写进 README

**验收标准**

- 能准确说出板子的 Kernel / U-Boot / 设备树 / 工具链版本，且这些结论有出处（启动日志或 BSP 文档），不是猜的
- 不看教程也能独立完成"写 → 编译 → 部署 → 运行"闭环
- `labs/00-toolchain/` 有源码、Makefile/脚本、README，且已提交
- 串口启动日志已保存为基线文件

**常见错误**

- 拿宿主机内核 `7.0.0-31-generic` 当板子内核 —— **这是本阶段最容易犯的错误**
- 脚本里直接用 `arm-linux-gnueabihf-gcc` 而不指定路径 —— 非交互式 shell 拿不到 PATH，会报 command not found
- 忘记给传过去的程序加可执行权限（`chmod +x`）
- 用错波特率导致串口乱码
- 把 BSP、内核源码、工具链压缩包误提交进仓库（`.gitignore` 已覆盖，但压缩包若改过名字可能漏网）

### Stage 1：Linux 基础与命令行

**学习目标**
能用命令行自如操作 Linux，理解权限、进程、文件系统的运作方式。

**前置知识**
Stage 0 的闭环已打通（能部署程序到板子）。

**需要学习者亲自动手完成的练习**

1. 写一个板子状态巡检脚本（CPU 温度、内存、磁盘、网络、关键进程）
2. 用 `ps` + `/proc/<pid>/*` 解剖一个进程，观察内存映射、打开的文件、环境变量
3. 把自己写的一个程序做成 systemd 服务并开机自启，用 `journalctl` 看日志
4. （可选）在板子上实现同样的自启 —— 注意板子通常没有 systemd，要用 busybox init 或 SysV 脚本

**验收标准**

- 不用图形界面，仅靠命令行完成查找、过滤、批处理
- 能说清 `/proc` 与 `/sys` 的区别
- 巡检脚本能实际在板子上跑出结果

**常见错误**

- 把脚本写成一次性命令的堆砌，没有参数、没有错误处理
- 混淆 `/proc`（内核暴露的运行状态）与 `/sys`（设备与驱动的属性接口）
- 在板子上找不到 `systemd` 就以为学错了 —— 板子的 init 系统与桌面版本来就不同

4. 把 `~/IMX6ull/pratice/02_arm_led_control.c` **重写**为 `labs/` 下的规范版本（补 `close`、正确的错误码、先 export GPIO、加 Makefile），**这是把历史练习纳入仓库的最佳切入点**

**验收标准**

**常见错误**

### Stage 3：进程、线程与 IPC

**学习目标**：理解 Linux 并发模型，写出正确健壮的多进程/多线程程序。
**前置知识**：Stage 2。
**亲自动手的练习**：生产者-消费者有界队列；**故意制造一次竞态**再用锁修正；多线程日志模块；简化版 shell（`fork`+`exec`+`wait`）；故意制造死锁并用 gdb 定位。
**验收标准**：能判断并发代码哪里会出问题；能解释 `fork` 之后父子进程的内存与 fd 关系。
**常见错误**：以为多线程 `++` 是原子操作；忘记 `pthread_join` 导致资源泄漏；在信号处理函数里调用非异步安全函数。

### Stage 4：网络编程

**学习目标**：写出稳定的 TCP 服务端/客户端，理解应用层协议设计。
**前置知识**：Stage 3。
**亲自动手的练习**：TCP echo；用 `epoll` 改造为多客户端并发并处理异常断开；自己设计带长度前缀的协议并处理粘包（可对照 CAN 的 `ID+DLC+Data` 思路）；让板子作为客户端连回开发机。
**验收标准**：能解释粘包成因与解法；能读懂 WebSocket 帧结构（**不要求自己实现协议栈**）。
**常见错误**：忽略 `EAGAIN`/`EINTR`；忽略 `send` 的部分发送；`epoll` 边缘触发模式下没有循环读到 `EAGAIN`。

### Stage 5：字符设备驱动

**学习目标**：理解驱动运行模型，写出规范的字符设备驱动。
**前置知识**：Stage 2；**Stage 0 的版本信息必须先确认**（不同内核的 `file_operations` 与注册方式不同）。
**亲自动手的练习**：第一个内核模块（`printk`/`dmesg`）；支持 `open/read/write/release` 的最简字符设备；加 `ioctl` 与用户态测试程序；多线程压测后再加锁。
**验收标准**：能说清为什么用户空间 buffer 不能直接解引用；能解释 `file_operations` 每个回调的调用时机。
**常见错误**：把宿主机内核头文件当目标内核头文件；忘了 `insmod` 后要 `mknod` 或依赖 `udev` 创建设备节点；在中断上下文里睡眠。

### Stage 6：设备树、GPIO 与中断

**学习目标**：看懂并修改板子设备树，把外设接到自己的驱动上，写带中断的驱动。
**前置知识**：Stage 5；**设备树文件必须在 Stage 0 拿到**。
**亲自动手的练习**：先用标准 binding（`gpio-leds`/`gpio-keys`）改设备树点亮 LED；写 `platform_driver` 通过 `compatible` 匹配；按键中断 + 去抖。
**验收标准**：能解释 pinctrl 配错的后果；能把自己的设备树节点与驱动对应起来。
**常见错误**：改了设备树但没重新编译 `dtb`；pinctrl 与 GPIO 声明不配对；引用了其他内核版本的 binding 示例。
**注意**：用户态访问 GPIO 的多种方式**只需了解，不必三套都深入**（这是学习者明确要求的）。

### Stage 7：总线与外设（重点 CAN）

**学习目标**：用 Linux 的方式访问板级总线，重点是 CAN。
**前置知识**：Stage 6；板子需要有 CAN 接口或外接 CAN 设备。
**亲自动手的练习**：SocketCAN 收发（`candump`/`cansend`）；用 C 收发 CAN 报文并映射为应用数据结构；用 `i2cdetect` 扫描 I2C 总线。
**验收标准**：能在 Linux 下用 C 稳定收发 CAN 报文；能判断哪些外设用用户态访问就够、哪些必须写驱动。
**常见错误**：忘记先 `ip link set can0 up type can bitrate ...`；把裸机 CAN 控制器编程习惯直接搬到 SocketCAN。

### Stage 8：OCPP 云平台 + i.MX6ULL 模拟充电桩

**学习目标**：完成可演示的完整系统。
**前置知识**：Stage 4（网络）+ Stage 3（并发）+ Stage 6/7（硬件）。
**实施顺序（不可颠倒）**：

1. **主线**：先在开发机上做纯软件原型，把客户端与服务端的完整充电流程跑通
2. **主线**：移植到 i.MX6ULL，打通 `Ubuntu CSMS ↔ OCPP ↔ i.MX6ULL ↔ 充电桩状态机`
3. 增强：GPIO 接入（继电器、指示灯、插枪按键）
4. 增强：**CAN 模拟 BMS**（**必须在主线跑通之后，不是前置条件**）
5. 增强：数据持久化与离线补传
6. 增强：异常场景（断网、服务端重启、掉电重启）

**验收标准**：能解释每一处技术选型的理由与代价。
**常见错误**：一上来就接硬件，导致协议问题和硬件问题混在一起无法定位。
**注意**：**WebSocket 使用成熟库，不要自己实现协议栈**（学习者明确要求）。

### 8.6 如何避免 AI 代替学习者完成全部学习任务

这是本项目的核心风险，也是学习者反复强调的要求。

1. **严格区分三类代码**（roadmap 7.2）：模板/重复性代码可以直接生成；工程代码要让学习者能讲清关键逻辑；**核心逻辑（`fork`/pthread/socket/`epoll`/`file_operations`/设备树节点/状态机/OCPP 消息）必须学习者先写**。
2. **遇到 bug 时先给排查方向**，不要直接贴答案。明确按学习者要求的措辞回应："先别给答案，告诉我该往哪个方向排查"。
3. **不要输出完整的实验代码**。学习者写好之后可以 review、可以指出问题，但不要替他写出第一个版本。
4. **用三问检验**：为什么这样写？换个写法会怎样？删掉某一行会发生什么？答不上来就说明这段代码不属于他。
5. **不要把 AI 完成的工作记成学习者的进度**。本章 3.1 已经做了区分，后续更新进度时请继续维持这个区分。
6. **commit 历史必须真实**。不要替学习者写提交信息，也不要把自己生成的代码直接提交。
7. **允许加速重复劳动**。学习者已经掌握的、纯重复性的内容，直接给结果即可，不要为了"教学"而故意绕弯子——那会让他失去耐心。
